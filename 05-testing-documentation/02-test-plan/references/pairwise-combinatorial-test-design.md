# Pairwise Combinatorial Test Design

Load this reference from Step 4 of the test-plan skill when a feature's behaviour depends on several interacting parameters and exhaustive testing of every combination is too costly to justify.

Method paraphrased from omkamal/pypict-claude-skill (MIT, https://github.com/omkamal/pypict-claude-skill, commit fbda212bca79dfa7611be12527b102c89cc8faeb) and Microsoft PICT (MIT, https://github.com/microsoft/pict, commit ab76c2548f551fcb46314e58653a1bd1172f3a72). ## 1. When to Use the Technique

Pairwise (2-way) combinatorial design is appropriate when all of the following hold:

- the feature has three or more parameters whose values interact, such as payment channel, connectivity state, currency and role;
- the parameters form a configuration, permission or environment matrix (device, locale, currency, tenant plan, feature flag); and
- the full Cartesian product is too large to execute in every regression cycle.

Most interaction faults in such features are triggered by the combination of two parameter values. A pairwise set exercises every allowed pair of values at least once, so it catches those faults with a fraction of the exhaustive case count. It complements, and does not replace, equivalence partitioning and boundary-value analysis: those techniques choose the values; pairwise design chooses how the values are combined.

## 2. Building the Model

### 2.1 Parameters and values

List each parameter that the SRS shows to influence the outcome. Every parameter shall be traced to the functional or non-functional requirement that makes it relevant (for example, `FR-PAY-003` for the payment channel). A parameter without a trace is either an elicitation gap, to be flagged `[TRACE-GAP: parameter]`, or an unnecessary dimension, to be removed.

Choose values by equivalence partitioning: one representative per equivalence class, plus boundary representatives where a numeric boundary matters. Keep value lists short; each extra value multiplies the pairs to be covered.

### 2.2 Constraints

Record every combination that the system cannot produce or that the SRS forbids, and state it as a conditional rule in plain language: when parameter A takes a given value, parameter B is restricted to certain values. Each constraint shall cite the requirement or business rule that justifies it. Constraints remove impossible cases from the set; they also remove the pairs they forbid from the coverage target, so a set is judged against *allowed* pairs only.

A constraint that has no requirement behind it is a hidden assumption. Raise it with the product owner before the set is generated, because an unjustified constraint silently removes coverage.

### 2.3 Generating the set

The reference generator is Microsoft PICT, which reads a parameter-and-constraint model and emits a covering set. Its installation is not required: for small models a hand-built table is acceptable, provided coverage is proved mechanically (see the worked example and `engine/tests/test_pairwise_example.py`). Record the tool and version, or "hand-built", in the coverage statement.

## 3. Coverage Statement

Every pairwise set in a test plan shall carry a coverage statement in this form:

> This set covers all 2-way interactions of N parameters (V1 x V2 x ... values), with K constraints, in M test cases, against a full product of P combinations. Generated by <tool and version | hand-built and mechanically verified>. Parameters trace to <FR/NFR IDs>.

The statement makes the claim auditable: a reviewer can recompute the allowed pairs and check the table.

## 4. Limits

- Pairwise design does not detect faults that need three or more specific values at once. Use 3-way (or higher) coverage for any path where a fault could harm a patient, lose or misdirect a payment, or corrupt a statutory filing; use exhaustive testing where the product is small enough to afford it.
- Coverage is only as good as the value choice. A missing equivalence class is not rescued by combinatorial design.
- Expected results are still needed for every case. A covering set says which inputs to combine, not what the system shall do; derive each expected result from the traced requirement.

## 5. Citing the Technique

ISO/IEC/IEEE 29119-4 (test techniques) classes pairwise testing among its combinatorial test design techniques. Cite 29119-4 for the technique and 29119-3 for the documentation of the resulting test design specification, verifying the exact clause number against the edition held before quoting it in a client deliverable.

## 6. Worked Example: Mobile-Money and Card Payment Capture

A Ugandan SaaS point-of-sale product captures payments. The SRS makes four parameters relevant (requirement IDs are illustrative):

- **Channel** — `FR-PAY-003`: MTN MoMo, Airtel Money or card.
- **Connectivity** — `FR-PAY-011`: the device is online, or the payment is queued offline for later submission.
- **Currency** — `FR-PAY-007`: UGX or USD.
- **Role** — `FR-PAY-015`: cashier, supervisor or administrator.

Constraint (`BR-PAY-002`): card payments require live authorisation, so a card payment can never be queued offline.

### Model

```pairwise-model
param Channel: MTN MoMo | Airtel Money | Card
param Connectivity: Online | Offline-queued
param Currency: UGX | USD
param Role: Cashier | Supervisor | Administrator
constraint: Channel = Card -> Connectivity = Online
```

The full product is 3 x 2 x 2 x 3 = 36 combinations; the constraint removes the six card-offline combinations, leaving 30 valid cases for exhaustive testing.

### Pairwise test set

| Case | Channel | Connectivity | Currency | Role |
|---|---|---|---|---|
| PW-01 | MTN MoMo | Online | UGX | Cashier |
| PW-02 | MTN MoMo | Offline-queued | USD | Supervisor |
| PW-03 | MTN MoMo | Offline-queued | UGX | Administrator |
| PW-04 | Airtel Money | Offline-queued | USD | Cashier |
| PW-05 | Airtel Money | Online | UGX | Supervisor |
| PW-06 | Airtel Money | Online | USD | Administrator |
| PW-07 | Card | Online | USD | Cashier |
| PW-08 | Card | Online | UGX | Supervisor |
| PW-09 | Card | Online | USD | Administrator |

Nine cases is the minimum possible here, because Channel x Role alone has nine pairs, each needing its own case.

### Coverage statement

> This set covers all 2-way interactions of 4 parameters (3 x 2 x 2 x 3 values), with 1 constraint, in 9 test cases, against a full product of 36 combinations (30 valid). Hand-built and mechanically verified by `engine/tests/test_pairwise_example.py`. Parameters trace to FR-PAY-003, FR-PAY-007, FR-PAY-011 and FR-PAY-015; the constraint traces to BR-PAY-002.

Each case then becomes a full 29119-3 test case with preconditions, steps and a deterministic expected result. Because an offline-queued mobile-money payment that is later reversed touches the ledger, the payment-reversal path is a candidate for 3-way coverage under Section 4.
